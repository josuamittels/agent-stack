# Ship

> **Skill** · **experimental** · **v0.9.0** · updated 2026-11-11

## Purpose

Use Ship to prepare and deliver an authorized repository change through the target repository’s supported release path.

## Workflow

1. **Check the repository release rules.** Read its contribution, check, and release instructions before choosing a delivery route.
2. **Review the change.** Inspect the working tree and relevant checks, resolve issues in scope, and keep unrelated changes intact.
3. **Deliver through the requested path.** Prepare the authorized commit or pull request using the repository’s conventions. Do not create a branch unless you explicitly ask for one; if the delivery requires a new branch, ask before creating it.

For Agent Stack, Ship first applies Release Agent Stack’s metadata, discovery, and documentation updates, then has Release Agent Stack run `npm run build` and the full `npm run build:preview`. Non-draft stacks also run `npm run package`; experimental stacks may ship at 0.y.z, while stable stacks require version 1.0 or later. Shipped components retain their experimental or stable labels; drafts are excluded. Ship verifies the generated archive checksums and final required checks before each commit. Generated packages and installation documentation belong to the matching commit. Build failure stops delivery; this step does not promote statuses or publish artifacts.


## Inputs

Use the user’s requested change and delivery boundary, repository root, available worktree and Git state, repo instructions, release metadata, declared checks, and available host tools. Resolve the repository root before reading project-level release files.

## Result

Return the completed commits and delivery state, version/changelog updates, applicable checks and their evidence, hosted request URL when created, and unresolved blockers. State whether work is local, pushed, under review, merged, or released. Never call a pending state complete.
